# Browser draft recovery

New and existing document editors save drafts under the authenticated account, document organization, document identity (`new` for creation), and a unique editor instance. Each mounted editor gets its own identifier, so separate or duplicated tabs do not overwrite one record. Returning to the form shows matching drafts and requires an explicit restore action. Restoration leaves the source record intact in case another tab still uses it.

Existing-document recovery is offered only after loading an editable document. It retains title, exact Markdown, category, tags, review date, visibility, and the original server timestamp. **Compare draft** shows the saved document beside the browser copy. Restoring copies the fields into the editor and pauses autosave until **Save Now** is used. Restoration does not move a document between folders or organizations. Replacing current unsaved editor text requires confirmation. Successful saves clear the current editor's copy only when no newer edits were typed during the request; independent source copies remain available for explicit discard.

A rejected concurrent save fetches the latest readable server version and presents its text and metadata beside local edits. Users can combine changes in the editor, explicitly accept that server version as their baseline, and then save. Accepting the baseline alone does not write data or resume autosave. The save still sends `expectedUpdatedAt`, so another server change produces another conflict instead of being overwritten. This is a manual comparison workflow, not an automatic three-way merge.

Drafts retain exact Markdown and form metadata. They expire seven days after their last write; expired matching records are removed when recovery is read. Drafts live only in this browser, are not encrypted independently of browser storage, and are not a server backup. Browser data deletion or storage eviction can remove them.

The UI reports storage failures without showing a successful save timestamp. It warns on page unload while edits remain unsaved, and intercepts ordinary link navigation when the latest browser draft is not protected. This does not yet cover every programmatic navigation or history action under storage failure. Organization selection remains usable if browser storage is blocked.

Sign Out clears these draft records and the old unscoped draft key. It changes a browser epoch so an already-open editor cannot recreate cleared drafts; other new-document tabs hide their editor when they observe the epoch change. If clearing storage fails, sign-out warns the user. Local persistence is keyed only after the profile request identifies the account. Legacy unscoped drafts are not automatically opened or attributed to a user, because their ownership is unknown; they are otherwise left untouched until explicit sign-out cleanup.

Current verification: storage unit tests cover account/org/document separation, tab independence, Markdown preservation, expiration, malformed/legacy entries, organization mismatches, quota errors, and post-logout write rejection. Browser verification created a synthetic draft, left through Cancel, returned, and restored the exact title/body through Restore a copy. The synthetic draft and recovered copy were cleared afterwards.

`npm run test:browser` runs Chromium against `TEST_BASE_URL` using the disposable administrator password in `SMOKE_PASSWORD`. It logs in once, reuses the session in isolated browser contexts, and logs out afterwards. Document reads/writes use synthetic intercepted API responses, so no document fixtures are written to the database. Tests exercise failed network saves and reload recovery, exact Markdown, independent tabs, switching documents, storage denial and cancelled link navigation, cross-tab logout epoch invalidation, and concurrent-save comparison. These browser tests validate client behavior; the separate live API reliability suite validates actual server authorization and concurrency. CI runs both.

Still pending for the platform goal: comprehensive programmatic/history navigation handling; idempotent creation; automated browser coverage for direct account switches, actual logout storage failures, rapid delayed-response document switching, full offline transitions, and repeated submissions. Browser-local drafts are not a replacement for backups. Do not treat this implementation as completion of the whole editing milestone.
